## 1. 当日までにそろえるもの

### 端末・アプリ

| 役割 | 必須条件 |
|---|---|
| iPhone A | 実機、iOS 17.0以上、内部 TestFlight の対象ビルドをインストール済み。テスト専用の未ペア・初回利用アカウント。OSカバレッジ用に最低対応の 17.x を推奨 |
| iPhone B | 実機、iOS 17.0以上、同じビルドをインストール済み。テスト専用の未ペア・初回利用アカウント。OSカバレッジ用に実施日時点の最新公開iOSを推奨 |
| OSカバレッジ | A/B で 17.x と最新公開iOSの2点を踏む。2台で満たせない場合は、実施したOSだけを記録し、未確認OSを「確認済み」にしない |

| ウィジェット | B のホーム画面に Lien の S ウィジェットを設置。A 完了時に、右側（相手）の完了印が変わるのを見る |

| 回線 | Wi-Fi またはモバイル通信が使えること。オフライン項目では A だけ機内モードを使う |
| 充電 | A/B とも50%以上、または充電器につないでおく |

端末の導入、TestFlight 処理待ち、OS 更新、ウィジェット追加、アカウント復旧は30分枠の前に済ませる。新規アカウントを作れない、A/B でビルド番号が違う、B のウィジェットや通知を用意できない、A にテスト画像がない場合は開始せず「BLOCKED」と記録する。実ユーザーのアカウント・記録をリセットしない。

通知を許可すると push token と APNs 環境はアプリが自動で保存する。手動で DB を編集しない。TestFlight は production の APNs を使うため、サーバー側の環境切り替えも不要。

### 用意するもの

- 1人の実施者、タイマー、記録表(§3)、失敗時 Issue 雛形(§4)
- A/B で区別できるテスト用ニックネームと約束。例: A=あお / 🚶 散歩、B=みどり / 📚 読書
- 写真項目用のテスト画像1枚。実在人物・位置情報・顧客情報を含めない
- A/B の機種名・iOS バージョン・TestFlight ビルド番号を、30分の計測開始前に記録
- 両端末の時刻は自動設定（Asia/Tokyo）。通知・ウィジェットの到達時刻を同じ時計で記録できるようにする
- 招待ページ（QR の飛び先）が開くこと。開かない場合は #4 を BLOCKED にし、コード手入力で #5 以降を続ける（QR の合格にはしない）

再実施で前回のペア・記録が残っている場合は、テスト専用アカウント2つに限り `products/lien/supabase/scripts/e2e_reset.sql` の手順で初期化する。実ユーザーのIDを入れず、実行前に対象IDをオーナーが目視確認する。この初期化は30分枠の外で行い、エージェントは実行しない。

招待コード、QR、ユーザーID、push token、認証情報は記録・Issue・スクリーンショットへ載せない。必要なスクリーンショットはニックネーム等をテスト値にし、コードや個人情報が映る部分を除く。

## 2. 30分の実行手順

端末A/Bを1人で交互に操作する。各枠は操作・目視・記録を含む。画面遷移を待つ間にもう一方の端末を操作する。失敗した項目は再試行で時間を使い切らず、表に時刻と実際の表示を残す。

#2 で B も約束を保存するのは、ペアは各自の約束を持ち寄るため（#6 で互いの約束を見る）。B が約束設定のままだと #4 の招待シートも開かないので、先に保存する。

### 2.1 つまずき時の対処

その場の対処は各項目の枠内で行い、待機は最大60秒まで。直らないときは、時間を使い切らずに結果と実際の表示を記録して次へ進む。回避できても PASS と区別し、気づきに「回避策を使った」と残す。

| つまずき | まず見る | その場の対処 | 記録 |
|---|---|---|---|
| QR を読んでも Lien が開かない | Safari の招待ページまで来ているか | ページの「アプリで開く」を押す。開かなければ B の「相手を招待する」→「コードを入力」へ A のコードを手入力 | 回避できたら PASS + 気づき。だめなら FAIL |
| B が約束設定のまま | 「あなたの約束をきめよう」が出ている | B で約束を保存する。保留中の招待コードでシートが自動で開く。QR を読み直さない | 回避できたら PASS + 気づき |
| A の招待シートが閉じない | B はペア成立済み、A はソロ | 30秒待つ → A を前面に戻す/再起動。B で再受諾しない | 再起動で直れば PASS + 気づき、直らなければ FAIL（P1候補） |
| B に通知が来ない | 集中モード、通知許可、電波 | 集中モードOFF、設定 > 通知 > Lien が「許可」を確認。B をホーム画面にして60秒待ち、通知センターも見る | 60秒超は FAIL（P2候補）。アプリを開いて同期しただけなら push 起点ではないと記録 |
| S ウィジェットが変わらない | B のホームに S ウィジェットがあるか | B で Lien を一度開いてホームへ戻り、60秒待つ。当日中にウィジェットを入れ直さない | アプリを開いて初めて変わったら push 起点ではないと記録。60秒超は FAIL（P2候補） |
| チェックイン/取消が失敗 | 画面のエラー文言、機内モード | 1回だけ再試行する。連打しない。オフライン項目なら機内モードと復帰を確認 | 2回失敗で FAIL。時刻と文言を残す |
| 写真を添えられない | テスト画像の有無、PhotosPicker が開くか | A の写真アプリにテスト画像があるか確認し、iCloud から未ダウンロードなら端末に保存する。PhotosPicker で選び直す | 画像を選べても送れないなら FAIL。画像が用意できないなら BLOCKED（環境） |
| B に A の写真が出ない | A の「今日の写真を添えました」、B のホーム | A で添付完了を確認。B を前面に戻す/再起動して同期を待つ。同じ写真を再送しない | 出なければ FAIL（P2候補） |
| 4回目の「つつく」が送れる | 上限文言の有無 | それ以上送らず、4回目に送れた事実だけ記録 | PASS にせず、P2候補として起票 |
| 片方だけペア/完了状態が違う | A/B のホーム、最終同期時刻 | 両方を前面にして30秒待ち、アプリを再起動。ペア解消はしない | 直れば PASS + 気づき。直らなければ FAIL（P1候補） |
| クラッシュした | 落ちた画面、再現操作 | 1回だけ再起動して同じ操作を試す。2回目も落ちたら中断 | P1。再現手順と画面録画を残す |
| 30分を超えそう | 残り項目と時計 | 現在の項目を FAIL/BLOCKED で記録し、残りは未実施にする。時間を縮めて PASS にしない | 全体は FAIL |
| コード・個人情報を写した | スクショ/画面録画の映り込み | 共有しない。ファイルを削除し、Issue には値でなく場所と影響だけを書く | セキュリティ事故として qa-lead へ報告 |

### 当日の終了判定

- **PASS**: 12/12 PASS。未解決 P0/P1 が0件。結果表と端末・OS・ビルド情報が埋まっている。
- **FAIL**: 1件以上 FAIL、または P0/P1 がある。アプリを「M1 E2E 合格」と扱わず、§4の雛形で Issue 化する。
- **BLOCKED**: 前提不足・配信環境障害などで実施不能。未実施を PASS にしない。原因と再実施条件を記録する。

### 重大度と判定

| 重大度 | 判定例 | M1判定 |
|---|---|---|
| P0 | 他人へのデータ露出、同意なし送信、意図しない課金・不可逆操作など、取り返しのつかない影響 | 即時中断。公開不可 |
| P1 | クラッシュ、記録消失/誤更新、ペア相手の取り違え、M1コアフローが完了不能、通知・ウィジェットが別人の状態を表示 | M1不合格。未解決なら公開不可 |
| P2 | コアフローは完了できるが、1項目の期待表示・同期が不安定で回避策がある | FAILとして起票。公開判断材料に残し、qa-leadが処置を判定 |
| P3 | 意味・状態を誤認させない軽微な見た目/文言差 | 記録して起票。M1合否は他の結果と重大度で判定 |

起票したら §3 の「起票 Issue」欄に番号を書き、P0/P1 はその場で qa-lead と orchestrator へ渡す。P0 は即時中断。修正後の再実施は、該当項目と影響を受ける経路に絞る（ペアを作り直す必要がある場合は #1〜#6 も再実施）。個人データの混入が疑われる証拠は共有せず、Issue には値でなく保管場所・影響範囲だけを書く。
