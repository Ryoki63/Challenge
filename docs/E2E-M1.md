## 1. 実施ランブック(2台の実機準備 → 各項目実施)

### 1.1 前提: Mac + Xcode が必須

本チェックリストはプッシュ通知・ウィジェット・App Group・写真撮影を含むため、**シミュレータでは実施不可(push 通知は実機のみ)**。実施には以下が明示的に必要:

- **Mac(Apple Silicon 推奨)+ Xcode**(`products/lien/ios` を `xcodegen generate` → `.xcodeproj` を開いてビルドするため)
- Apple Developer Program 加入済みアカウント(署名用。G0/#38)
- iPhone 実機 **2台**(iOS 17.0+。REQUIREMENTS §4)
- Supabase 本番プロジェクト(ref `lniheehfbtpfhglinfjm`)への到達性(デプロイ済みのEdge Functions/DB)

### 1.2 デバイス導入(2経路。詳細手順は `products/lien/scripts/g1/RUNBOOK.md` 手順6を参照し、ここでは重複させない)

G1 RUNBOOK が定義する2経路をそのまま使う:

- **経路A(推奨): Xcode automatic signing** — Mac で `xcodegen generate` → Xcode で Team 選択・自動署名 → iPhone 2台にUSBで直接 Run。この経路は **APNs 環境 = sandbox**(development 署名。端末が `push_env = sandbox` を自動で保存し、サーバーはトークンごとに環境を選ぶ — §1.3)
- **経路B(フォールバック): ad-hoc IPA 配布** — UDID登録+ad-hocプロファイル+CI署名ビルド→ Apple Configurator等で導入。証明書管理の手間が大きいため、Macが使えるなら経路Aを推奨

どちらの経路でも、2台には**別々の匿名アカウント**でオンボーディングを完了させる(端末A・端末Bとして以下すべての項目で使用)。

> **TestFlight配布で実施する場合の注意**: TestFlight は production の APNs。アプリが `push_env = production` を自動で保存し、サーバーはトークンごとに環境を選ぶので、サーバーの `APNS_ENV` を切り替える必要はない(§1.3 / DESIGN §4.1・§10)。sandbox(Xcode直接インストール)で合格しても **production環境の挙動は未保証** — G3(本提出前の最終確認。issue #41)で TestFlight 配布に切り替えた際に本チェックリストの該当項目(特に⑥通知とウィジェットの反映・⑨つつく)を再実施すること。

### 1.3 push トークンの登録

- 通知許可後に `PushManager` / `AppDelegate` が APNs 登録を行い、デバイストークンを受け取る(`products/lien/ios/Lien/Core/PushManager.swift`, `App/AppDelegate.swift`)。**通知を許可していない端末は APNs 登録が始まらない**ので、①でどちらの端末も「通知を許可する」を選ぶこと
- **`users.push_token` / `push_env` はアプリが自動で保存する**(`PushTokenSync`。W1 #55 で実装、#62 でサーバー側のずれの確認を追加。DESIGN §3.3・§4.1)。トークンの取得とセッションの確立の両方がそろった時点で送り、変化時だけ送る。`push_env` は署名の `aps-environment` から判定する(Xcode 直インストールの development 署名 = sandbox / TestFlight = production。`APNsEnvironment.swift`)。**手動で PATCH する必要はない**(以前は G1 と同じ手動登録の手順だった。`SUPABASE_SERVICE_ROLE_KEY` を手元で使う手順は不要になった)
- 保存されたかの確認が要るときは、Supabase ダッシュボードの Table Editor で `users` の `push_token` / `push_env` が入っていることを人間が見る(DEBUG ビルドのホームに出る「Device Token(G1計測用)」= `DeviceTokenDebugView.swift` の先頭と、`push_token` の先頭が一致する)。Release / TestFlight のビルドには DEBUG の表示が無いので、`push_env` が `production` で入っていることだけを見る
- APNs の環境は**トークン単位**(DESIGN §4.1): サーバーの `APNS_ENV` は `push_env` が未設定のトークンのフォールバックにすぎないので、開発ビルドと TestFlight の端末が混在していても両方に届く。環境が合わないトークンは `400 BadDeviceToken` になり、サーバーが `push_token` を null にする(次の起動か、1時間以上あけた前面復帰でアプリが再登録する)

### 1.4 計測方法(項目⑥: ウィジェット反映60秒以内 p50)

G1 RUNBOOK 手順7の `measure.sh` と同じ方法論を使う: ストップウォッチで「checkin POST(T0)→ 相手端末のウィジェット/通知表示(T1)」を**10回計測**し、p50 ≦ 60秒かを判定する。G1がM0時点の技術検証、本項目⑥はM1完成形(本物のUI操作+通知経由)での再確認という位置づけ。

### 1.5 e2e_reset.sql の使い方

12項目を複数回実施(リトライ含む)するとテストユーザーのペア/チェックイン等が積み重なる。各回の実施前に `products/lien/supabase/scripts/e2e_reset.sql` でテスト専用ユーザー2名分のデータだけを初期状態に戻せる(詳細は同ファイル冒頭のコメントを参照)。**本番Supabaseに対して実行する前に対象ユーザーIDが本当にテスト用であることを目視確認すること**。

### 1.6 記録方法

12項目それぞれ実施後、§2の表の「合否」列に ✅/❌ と実施日・実施者を記入し、`progress/JOURNAL.md` に結果を追記、issue #20 に完了コメントを投稿してからクローズする(この最終ステップは本タスクの対象外)。
