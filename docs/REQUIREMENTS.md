## 1. 用語定義

| 用語 | 意味 |
|---|---|
| ペア | 2人1組の関係。v1 では 1ユーザー1ペアまで |
| 約束 | 各自が1つだけ持つ毎日の習慣(タイトル+絵文字+リマインド時刻) |
| チェックイン | 「今日やった」報告。1日1回、本人のローカル日付で判定 |
| ふたりストリーク | 2人とも自分の約束をチェックインした日の連続数。ペアに1つ |
| お休みチケット | 片方が未達でもストリークを守る保険。ペア共有在庫 |
| つつく | 未完の相手に送るナッジ通知。相手の名前で届く |
| 相棒(植物) | ペアで1鉢育てる植物。鉢に住むタネの子の頭から育つ。ふたり達成日の累計回数で成長 |
| ふたり達成日 | 2人ともその日の約束をチェックインした日(`streak_days` の kind='both')。ストリークと植物の成長の基準。お休みチケットの日は含まない |
| ふたりの葉 | タネの子の頭の双葉2枚。自分の画面では左=自分・右=相手。その日チェックインした人の葉がひらく |

## 2. ユーザーストーリー(v1.0)

1. 初めて開いた人として、30秒でコンセプトを理解し、ニックネームを設定して始められる
2. 誘う側として、招待リンク(またはQR)をLINEで送り、相手が入ったらペアが成立する
3. ペアの一員として、自分の約束(例: 筋トレ)を1つ設定し、リマインド時刻を決められる
4. 毎日の利用者として、やった日に1タップでチェックインし、気が向いた日は写真を添えられる
5. 相手として、パートナーがチェックインしたら通知とウィジェットで即わかる
6. サボりそうな日に、相手から「つつき」が(相手の名前で)届いてやる気になる
7. ふたりとして、ストリークが伸び、植物が育っていくのをウィジェットで毎日眺められる
8. うっかりした日も、お休みチケットが自動で消費されてストリークが守られる
9. 節目(7/30/100日)に、ふたりの記録画像を生成してSNSにシェアできる
10. [v1.0.1] 機種変更しても、Apple アカウント連携で記録を引き継げる(v1.0 は匿名認証のみ。機種変更で記録を引き継げない場合があることを、オンボーディングと設定で伝える。§3.1)

## 3. 機能要件

優先度: **[v1.0]** リリース必須 / **[v1.0 P1]** v1.0 に入れたい候補(必須ではない。工数に余裕があれば入れ、足りなければ GROWTH.md §6.1 の順で削る) / **[v1.0.1]** v1.0 公開直後の追加リリース(1月。2026-10-12 に v1.0 から外した機能の一部と花壇・おきゃくさん) / **[v1.1]** リリース後すぐ / **[v2+]** 収益が立ってから

### 3.1 アカウント
- [v1.0] 匿名(端末)で即開始できる。ニックネーム(8字)+アイコン(絵文字パレットから選択)
- [v1.0] 機種変更で記録を引き継げない場合があることを、オンボーディングと設定に表示する(匿名認証のみのため。文言は T27)
- [v1.0.1] Sign in with Apple 連携(任意だが、機種変更引き継ぎとペア復元の条件であることを明示。ペア成立後にやんわり促す)。v1.0 は匿名認証のみでサードパーティのログインを提供しないため、ガイドライン 4.8 の対象外と判断した(#24)
- [v1.0] リマインド時刻の設定(任意、デフォルト 20:00)
- [v1.0] アカウント削除(App審査要件のため設定画面に用意した — §3.15・§8。T23 #23 で実装済み。旧版は「[v2+] … 実体は v1.0 で用意する」と書いていた。実体が v1.0 にあるので、優先度の表記を直した)

### 3.2 ペア管理
- [v1.0] 招待発行: 8文字の英数字コード(大文字小文字を区別。紛らわしい 0/O/1/l は使わない — DESIGN.md §5.1)+QR+リンク(静的招待ページ経由で `lien://` スキームを開く方式。DESIGN.md §6)。ユニバーサルリンク化は独自ドメイン取得とセットで v1.1
- [v1.0] 招待の有効期限 72時間 / 1リンク1回限り
- [v1.0] **招待待ちでも使える**: ペア未成立でも約束設定とチェックインは可能(ソロ状態。写真はペア内の共有なので、ペア成立後に添付できる — #55)。ペア成立日からふたりストリーク開始。※「2人いないと何もできない」はApp審査リジェクトと初日離脱のリスクのため
- [v1.0] ペア解消: どちらからでも可能(確認2段階)。解消時の挙動 — 自分のチェックイン履歴は残る / 共有写真は相互に非表示 / 植物・ストリークはアーカイブ(復縁時も復活しない)
- [v1.1] 新しい相手との再スタート(ストリーク0から、新しい鉢)
- [v2+] 複数ペア(最大5、Duolingo方式)は**プレミアム特典**として解放(無料は1ペアのまま)。「2ペア目を作ろうとした瞬間」が最強の課金文脈になる

### 3.3 約束
- [v1.0] 1人1つ。タイトル(20字)+絵文字+リマインド時刻(任意)
- 約束は**ペアではなくユーザーに属する**。v2で複数ペアを持っても約束は1つのままで、1回のチェックインが全ペアに同時反映される(「約束はひとつだけ」を複数ペアでも維持。ペアが増えるほど「自分がサボると複数人をがっかりさせる」継続圧が働く)
- [v1.0] いつでも編集可。**約束を変えてもストリークは継続**(寛容設計。「約束を育て直す」のは前向きな行為として扱う)
- [v1.0] 相手の約束はホームに常時表示(お互いに何を頑張っているか見える)
- [v1.1] 曜日指定(月水金など)。指定外の日は「お休み日」としてストリーク判定から除外

### 3.4 チェックイン
- [v1.0] 1日1回。判定は**本人のローカル日付**(国内ペア前提。時差ペアの厳密対応はv2+)
- [v1.0] 1タップで完了 → 完了後に「写真を添える」ボタン(任意、その日1枚、ライブラリから選択)
- [v1.0.1] 写真をカメラで撮影して添える
- [v1.0] 取り消しは当日中のみ可(誤タップ対応)。過去日への遡及チェックインは不可(救済はチケットの役割)。取り消すと、先取りで表示していた植物の成長1回分も戻る(§3.9)
- [v1.0] オフライン時はローカルに記録し、接続時に同期(チェックインは冪等に設計)
- [v1.0] 完了時の演出: 自分の側の葉がひらき(段階0=たねの間は、葉の前の芽が光る)、植物がうれしそうに揺れる。相手が完了済みなら「ふたり達成!」の演出

### 3.5 ふたりストリーク
- [v1.0] 定義: 2人がそれぞれ自分のローカル日付でチェックインした日が連続した日数
- [v1.0] 片方未達の日: ペアのお休みチケット在庫があれば**自動消費して継続**(消費は両者に通知)
- [v1.0] チケットもない場合: リセット。ただし演出は責めない — 「また今日から。最高記録 ○日 はふたりの財産」(最高記録・累計達成日数・開始日は永続表示)
- [v1.0] 21:00 時点で片方未完なら「ストリーク危機」通知(これはアプリ名義)
- 設計原則(CONCEPT.md §5): 罰・恥の演出は一切入れない。リセット画面に相手を責める文言を絶対に置かない

### 3.6 お休みチケット
- [v1.0] ペア共有在庫。無料: 毎月1日に2枚付与(繰越なし、上限2)
- [v1.1] プレミアム: 毎月5枚(繰越あり、上限10)
- [v1.0] 自動消費(優先)。残数はホームにバッジで表示する(snapshot の `ticketBalance`)
- [v1.0.1] 事前の「お休み宣言」(明日休む、を相手に通知してチケット予約)。v1.0 は自動消費だけで罰なし原則(チケットで守る)が成り立つため、宣言 UI と専用の関数は後ろに回した(D3)
- [v1.0] 消費履歴はカレンダーに「お休み」マークで表示(達成と区別する)
- お休みチケットで守られた日は、ストリークは続くが、植物の成長には数えない(§3.9)

### 3.7 つつく(ナッジ)
- [v1.0] 相手が未完のときだけ押せる。1日3回まで
- [v1.0] 通知は**相手のニックネーム名義**。本文は定型文からランダム(20種程度) + スタンプ6種から選択
- [v1.0] **自由テキスト入力は入れない**(チャット化を避ける=LINEと競合しない・モデレーション不要・「静かなアプリ」ポジション維持)
- [v1.0.1] つつかれた側はワンタップで返事(「今やる!」「ごめん寝てた」等の定型4種)。v1.0 は通知を受け取るだけ(D3。記録先の列 `nudges.replied` は確保済みで未使用)
- 計測: つつき→2時間以内チェックイン率(このアプリの存在価値を示すコア指標)

### 3.8 リアクション
- [v1.0] 相手のチェックイン(と写真)にスタンプ1つ(❤️🔥👏😂🥹💪)。通知は自分の名前名義
- [v1.1] 写真へのリアクション履歴をアルバムで見られる

### 3.9 植物(相棒)
2026-10-12 改定(成長ルール v2。D1・D2)。設計の根拠・段階表・見え方の詳細は [GROWTH.md](GROWTH.md)。絵のレイヤーの規則と重ね順は `products/lien/assets/plant/mapping.md`(取込後)/ 現時点の正本は `products/lien/assets/plant/v4_drafts/README.md`
- [v1.0] ペアに1鉢。鉢には顔のある種「タネの子」が住み、頭から植物が育つ。タネの子(体・顔・名前)はずっと同じ子で、入れ替わらない
- [v1.0] ソロ状態(ペア未成立)では、タネの子は鉢の土の中で眠っている(自分がチェックインすると土がほのかに光る。一言は「ペアになると、タネの子が目をさますよ」)。ペア成立で目をさまし、頭に小さな芽が2つ出る(招待の動機付け)
- [v1.0] 成長は「ふたり達成日」(2人ともその日の約束をチェックインした日)の累計回数で決まる。お休みチケットの日は数えない。回数は減らず、ストリークが途切れても植物は縮まない。今日ふたり達成すると、その場で1回分を先取りして表示する(確定は close-day)
- [v1.0] 10段階: たね(0)→ふたば(1)→めばえ(3)→わかば(7)→よりそい(14)→つぼみ(21)→いろづき(30)→ほころび(45)→ふたりざき(66)→みのり(100)。名前は仮。閾値はサーバーの配列1本で持ち、調整は下げる方向のみ・段階の追加は末尾のみ
- [v1.0] ふたりの葉: 頭の双葉2枚は、自分の画面では左=自分・右=相手。その日チェックインした人の葉がひらき、まだの人の葉はたたんでいる(眠っているだけで、しおれない・色も大きさも変えない)。日付が変わると2枚ともたたむ。つぼみ・花は常にひらいている。段階0(たね)の間は葉がまだ無く、頭の2つの芽(左=自分・右=相手)が同じ役目をする(チェックインした人の芽が光る。ふたばで芽がひらいて葉になる。GROWTH.md §3.3・§4.1)
- [v1.0] 表情: ふつう / にっこり(ふたり達成の日。キラキラ)/ ひらいた葉の方をうれしそうに見る(片方だけ完了。閉じた葉は見つめない)/ すやすや(ふたり達成もお休みチケットもない日が昨日まで2日以上続き、今日まだ誰もチェックインしていない。API の値は `sad` のまま)。枯れない・後退しない(例外: 当日のチェックイン取消で先取り分が戻る)
- [v1.0] 次の段階までの残りをホームに文で表示する(例「ふたりそろって あと2回で つぼみ」。長い区間の前半は「わかばになってから 3回そろったよ」)。単位は「回」。ウィジェットは細いバーのみで、数字はストリークだけ
- [v1.0] 段階アップ(ペア成立=段階0を含む)は各段階1回だけ全画面で演出する。相手名義の通知には混ぜない
- [v1.0] 名前: 最初に「ふたば」になったときの演出の中で付ける。先に付けた人の名前に決まる。あとから変更でき、変更は相手に知らされる
- [v1.0] アセットは SVG のレイヤー(約30点)を重ねて描く。アニメは揺れ・葉の開閉・段階アップの演出のみ
- [v1.0 P1] のぞき(区間の途中の光る小さな芽)・おかえり・今日のひとこと・段階アップ演出の「ハートを送る」・名前の相手名義の通知。P1 は工数に余裕があれば入れる。時間が足りなければ GROWTH.md §6.1 の順で削る
- [v1.0.1] 100回以降: 25回(仮)ごとに、鉢の横の花壇に小さな花が1輪ずつ増える(置き換えない・減らない・期限なし)
- [v1.0.1] おきゃくさん: ふたり達成の日(2回目以降)に必ず1組来て、次のふたり達成の日まで滞在する。2人の画面で同じ子。段階が進むと来る子が増える。購入不可・確率なし・ハズレなし
- [v1.1] 花の色: 各自が自分の側の花の色を選ぶ(ほころび以降・いつでも変更可・無料)
- [v1.1] 品種(頭の植え替え)と鉢の着せ替えはプレミアム。品種はふたりざき(66回)以降に選べ、体・顔・名前・回数はそのまま。鉢はいつでも。成長の速さ・ランダムな品は販売しない。花壇・おきゃくさんの記録は無料
- [v2+] 複数ペア時: ホームは鉢が横に並ぶ**「窓辺」ビュー**(ペアの数だけ鉢が増える=人間関係の蓄積が一画面に見える)。チェックインは1タップで全鉢が一斉に反応する

### 3.10 ウィジェット(本プロダクトの主役)
- [v1.0] ホーム S: 2人の今日の状態(自分/相手の○×)+ストリーク数+植物(ふたりの葉が今日の2人を表す)+細い進み具合のバー(数字は出さない。数字はストリークだけ)
- [v1.0.1] ホーム M: S の内容+相手の今日の写真(なければ植物を大きく)。v1.0 は S とロック画面のみ(D3)。相手の写真は、当日のホーム画面で見られる

### 3.14 課金 [v1.1 で導入。v1.0 は全機能無料で継続データを取る]
- **個人課金、効果はペアに波及**: 課金した本人が属する**全ペア**にプレミアムが適用される。ペア内に課金者が1人いればそのペアはプレミアム。両方課金しても恩恵は重複加算しない(購入画面に「相手がすでにプレミアムなのでこのペアは適用済み」と表示して誤課金を防ぐ)
- 価格: 月700円 / 年2,400円(年額を推す。2026-06の相場調査による改訂、CONCEPT.md §6)
- 無料: 1ペア、約束1つ/人、チケット月2枚、写真30日、植物1品種、基本ウィジェット
- プレミアム: チケット月5枚+繰越、写真アルバム無制限、植物の品種・鉢替え、ウィジェットテーマ、「この日のふたり」、(v2)**複数ペア最大5**
- **プレミアムでも約束は1人1つを維持**(「約束はひとつだけ」が看板のため)
- **ただ乗りは意図的に許容する**: 課金者のペア相手は無料で恩恵を受けるが、(1)そのペアの解約率を下げる (2)プレミアム体験者=将来の課金候補を作る (3)口コミ・招待の装置になる。広告費ゼロの個人開発では、ただ乗りのコストより宣伝価値が大きい。一方で「たくさんペアを作る人」は2ペア目以降がプレミアム特典なので、ヘビーユーザーほど課金者になる構造
- 無料トライアル: 17日以上を基本線(転換率42.5%、CONCEPT.md §6)。v1.1実装時に最終化
- 実装: RevenueCat(Webhookで users.premium_until を更新)。ペイウォールは節目通知・アルバム30日超・チケット切れ・(v2)2ペア目作成の4文脈で出す(押し売りしない)

## 5. データモデル(Supabase / PostgreSQL)

```sql
users          (id uuid PK, apple_sub text? UNIQUE, nickname text, avatar_emoji text,
                timezone text, remind_at time?, push_token text?,
                premium_until timestamptz?,  -- RevenueCat Webhookで更新
                created_at)
                -- 2026-06-11 実装同期: apple_sub に UNIQUE(migration 0001)
pairs          (id uuid PK, status text /* active|dissolved */, started_on date,
                dissolved_at timestamptz?,  -- 解消時刻。dissolve処理が status と同時に設定
                ticket_balance int, created_at,
                CHECK ((status = 'dissolved') = (dissolved_at IS NOT NULL)))
                -- ペアのプレミアム判定はメンバーの premium_until から導出(planカラムは持たない)
                -- 2026-06-11 実装同期: dissolved_at と整合CHECKを追加(migration 0001)
pair_members   (pair_id FK, user_id FK, joined_at, PRIMARY KEY(pair_id, user_id))
promises       (id uuid PK, user_id FK, title text, emoji text,
                remind_at time?, created_at, archived_at?,
                UNIQUE(user_id) WHERE archived_at IS NULL)  -- 部分一意: 現役の約束は1人1つ
                -- 約束はユーザーに1つ(ペアに属さない)。v2複数ペアでもこのまま
                -- 2026-06-11 実装同期: 「1人1つ」の部分一意インデックスをDBでも担保(migration 0001)
checkins       (id uuid PK, promise_id FK, user_id FK, date_local date,
                photo_path text?, created_at, UNIQUE(user_id, date_local))
streak_days    (pair_id FK, date_local date, kind text /* both|ticket */,
                PRIMARY KEY(pair_id, date_local))   -- 現在値・最高値はここから導出しキャッシュ
ticket_ledger  (id PK, pair_id FK, delta int, reason text /* monthly|consume|declare */,
                date_local date, created_at)
nudges         (id PK, pair_id FK, from_user FK, stamp text, replied text?, created_at)
reactions      (id PK, checkin_id FK, from_user FK, stamp text, created_at,
                UNIQUE(checkin_id, from_user))  -- 1チェックインにつき1人1スタンプ(§3.8)
                -- 2026-06-11 実装同期: UNIQUE(checkin_id, from_user) を追加(migration 0001)
plants         (pair_id PK, species text, name text?, grown_days int, stage int)
                -- 2026-10-12 改定(成長ルール v2): stage は v1.0 では書かない。表示用の段階は、サーバーが streak_days の both の行数から計算する。grown_days は close-day が数え直して書く控え
                -- stage の CHECK(0〜5)は v1.0 では触れない(書かないので違反しない=migration 不要)。外すのは v1.1 の plants 改修と一緒に行う(GROWTH.md §7.2)
                -- name は 1〜8字。plant-name 関数が書く(first は null のときだけ、rename は上書き。DESIGN §5.3)
invites        (token PK, from_user FK, created_at, expires_at, used_at?)
                -- 2026-06-11 実装同期: created_at を追加(発行時刻の監査用。migration 0001)
```

- ストリーク判定は Edge Function(チェックイン書き込み時)で `streak_days` を更新 → サイレントプッシュ送信、の一本道にする

## 7. 計測(v1.0 は分析 SDK なし。DB から SQL で出す — 2026-10-12 D6)

- v1.0 は、分析 SDK(TelemetryDeck など)も、計測イベント用の自前テーブルも入れない。**アプリは計測のために何も送らない**。数字は、機能のために既にある Supabase のテーブルを SQL で集計して出す(読み取りだけ。開発者が手元で実行する)
- 理由: App Privacy の申告とプライバシーポリシーが単純になる。計測のためのアプリ改修が要らない(申告内容の最終確認は T30)
- 毎週金曜の `/status` で記録する(TASKPLAN §5)。SQL の例は [GROWTH.md](GROWTH.md) §10.1・§10.2
- 指標の名前は次のとおり残し、データ源を決めた:

| 指標 | データ源(SQL で出す) |
|---|---|
| 活性: `pair_created`(North Star の入口) | `pairs`(created_at・started_on) |
| 活性: `checkin` | `checkins`(created_at・date_local) |
| 活性: `both_done_day`(**North Star: 週あたりのふたり達成日数**) | `streak_days` の kind='both' の行数(ペア×週) |
| 介入効果: `nudge_sent` → `nudge_converted`(2時間以内に相手がチェックイン) | `nudges`(created_at)と、相手の `checkins`(created_at)の突き合わせ |
| 継続: D1/D7/D30 両者継続率 | `streak_days` の kind='both'。定義(仮): 成立日を d0 として、d0+n−2〜d0+n の3日間に both の日が1日以上あるペアの割合(1日休んだだけのペアを離脱と数えない。GROWTH.md §10.1) |
| 継続: `streak_reset` | 永続化しない(DESIGN §5.7)。`streak_days` の行が途切れた箇所から導出する |
| 継続: `ticket_consumed` | `ticket_ledger`(reason='consume')、または `streak_days` の kind='ticket' |
| 成長: `invite_sent` → `invite_accepted` 転換率 | `invites`(created_at・used_at) |
| 成長: 植物の指標(最初のふたば・名付け率・段階への到達など) | `streak_days`・`plants`(GROWTH.md §10.2) |
| 成長: `share_image_created` | 端末の中で作るので DB に残らない。v1.0 では計測しない |
| 収益(v1.1): `paywall_view`(文脈別)→`trial_start`→`subscribe` | DB に残らない。課金の導入時に、RevenueCat の分析で足りるか SDK を入れるかを判断する |

## 10. 保留事項

### v1.1 以降に判断

- **無料トライアルの長さ** — 17日以上を基本線(転換率42.5%の実績値)。v1.1 課金導入時にユーザーデータを見て最終化

- **あずけ**(植物の成長ルール。GROWTH.md §13.2) — 片方だけが達成した日を最大3日分とっておき、次のふたり達成の日に「ゆうきがとっておいてくれたよ」として足す案。「ふたりでしか育たない」原則を守ったまま頑張った側に報いられるが、借りがあるように感じさせない文言が要り、ルールが1つ増える
- **曜日指定(v1.1)との関係** — 片方がお休みの日に、もう片方だけが達成した日を、植物の成長に数えるか
- **しばらく離れている人への、アプリ名義のやさしい通知** — 3日目と7日目に1回ずつ、オフにできる案
- **植物を直接押す操作** — 植物の上でつつく・リアクションできるようにするか
