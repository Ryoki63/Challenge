## 3. status と承認の流れ

`status: draft` → `status: ready` の順でしか進めない。**mkt-exec（この下書き）は ready にしない。**

1. **mkt-exec（下書き）**: 各ファイルを作成し、`review.md` に主張→根拠の対応表を付ける。`status: draft`。
2. **mkt-lead（承認）**: 方針（看板・トーン・日付の扱い・投稿順）に合うか。`## 承認` の mkt-lead をチェック。
3. **mkt-review（レビュー）**: 景品表示法・誇大表現・体験していない機能の訴求・競合名・数値の根拠。`## 承認` の mkt-review をチェック。
4. **ready 化**: 両方が揃ったら `status: ready` にし、`review.md` の台帳に1行足す。
5. **投稿**: computer-operator が §7 の手順で投稿する（このリポジトリの作業ではない）。

検査 `tools/check_posts.py` は、`status: ready` なのに承認が欠けている／台帳に行が無い投稿を**エラーにする**。承認前に ready へ書き換える事故を機械的に止めるため。

## 4. 文章の原則（全投稿共通）

1. **看板は「約束はひとつだけ」**。機能の多さで語らず、削った理由で語る。
2. **罰・恥・煽りを使わない**（REQUIREMENTS §3.5 / DESIGN §3.8）。アプリ本体の禁止語 8 語（`枯れ` `サボ` `罰` `恥` `ダメ` `怒` `遅い` `まだやってない`）は投稿でも使わない。「失敗」「逃す」「急げ」「絶対」「必ず」も使わない（`aso.md` §4 の運用に合わせる）。
3. **v1.0 に無い機能を「ある」と書かない**。課金（v1.1）・アルバム無制限（v1.1）・Sign in with Apple（v1.0.1）・カメラ撮影（v1.0.1）・ウィジェット上のチェックイン（v1.1）・複数ペア（v2）は書かない。
4. **数値・順位・受賞を根拠なく書かない**。本文の数字はすべて `数値の根拠` に出处を書く（検査対象）。「No.1」「日本一」「唯一」「業界初」は使わない。
5. **競合名を出さない**（`docs/TASKPLAN.md` §9.4 の T32「Pairy 語は全廃」に合わせる）。比較で持ち上げず、自分の設計理由を書く。
6. **日付を断定しない**。本文に「10月31日」「10/31」「2026年」を書かない（検査対象）。
7. **写真・実在人物を出さない**。画像はアプリのアートと実機スクリーンショットだけ（REQUIREMENTS §3.13 のシェア画像も写真を含めない）。
8. **1投稿1メッセージ**。140 字に収める。ハッシュタグは 2〜3 個まで。

## 6. リンク先

| 種別 | リンク先 | 状態 |
|---|---|---|
| 開発ストーリー（公開前） | なし（プロフィールの固定ポストへ） | ストア URL が未確定のため。**欠測ではなく意図的な「なし」** |
| 公開日・公開翌日・1週間後 | `<APP_STORE_URL>` | ASC のアプリレコード作成（G0 後）で確定。確定まで `status: ready` にしない（検査で止まる） |

- App Store の URL は `https://apps.apple.com/jp/app/id<数字>` の形。ASC で App ID が決まったら、13 本の `リンク先` を一括で置換する。
- UTM は付けない。App Store は UTM を解釈せず、アプリ側も計測 SDK を入れていない（REQUIREMENTS §7 / D6）。X の投稿別インプレッションと、ASC の日次 DL を**別々に**見る。

## 7. computer-operator への渡し方（承認後）

1. `status: ready` の投稿だけを対象にする（draft は渡さない）。
2. 本文は `## 本文` の引用（`>`）を除いたテキストをそのまま使う。改行もそのまま。
3. 添付画像は `添付画像` のパスをアップロードし、`代替テキスト` を画像の説明欄に入れる。
4. リンク先が `なし` の投稿は、URL を本文に入れない（プロフィール導線のみ）。
5. 投稿後、投稿 URL を `review.md` の台帳に記録する。**予約投稿はしない**（日付が動いたときに取り消せないため）。
6. 公開日告知（`2026-10-31.md`）は、App Store で実際に公開されていることを確認してから投稿する。確認できない間は代替文面（近日公開）を使う。

## 8. この施策で見る数字（計測設計）

分析 SDK を入れない方針（D6）なので、アプリ側に新しい計測は足さない。見るのは次の 2 つだけ。

| 指標 | 出どころ | 分母 | 使い方 |
|---|---|---|---|
| 投稿のインプレッション / エンゲージメント / リンククリック | X のアナリティクス（投稿ごと） | インプレッション | どのテーマが読まれたか。リンククリック率 = リンククリック ÷ インプレッション |
| プロフィール訪問 → フォロー | X のアナリティクス（日次） | プロフィール訪問 | フォロー率 = フォロー ÷ プロフィール訪問 |
| DL 数（日次） | App Store Connect（公開後） | − | 投稿時刻との前後だけを見る。**X の数字と DL を1本の率にしない**（分母が違う） |

- 率を書くときは分母を添える。DL 数は ASC の実数のみで、X 側の数から推計しない。
- 効果測定の準備はこの表まで。投稿ごとの実数は、公開後に `review.md` へ追記する。

## 10. 検査

```bash
cd products/lien/marketing/x
python3 tools/check_posts.py          # 13本 + branding.md の静的検査（失敗時 exit 1）
python3 -m unittest discover -s tools -p "test_*.py"   # 検査自体の単体テスト
```

CI（`.github/workflows/lien-ci.yml` の `store-metadata` ジョブ）でも同じ2つを回す。下書きを足したときに、レビュー前に機械で落とせるものはここで落とす。

検査する内容: ファイル名と日付の連続性 / 必須フィールド / 本文 140 字以内 / 禁止語・誇大表現 / 競合名 / 日付の断定 / 本文の数字が `数値の根拠` にあるか / 根拠の節が実在するか / 添付画像のパスが実在するか / 承認が揃う前に `status: ready` になっていないか / `branding.md` の表示名・bio・@handle・固定ポストが同じ原則に沿っているか。
